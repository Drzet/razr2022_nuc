### Actual component producer and source-dependent branches

1. **Downloaded boot image:** Motorola's fastboot handler `0x8ca8–0x8e90` takes the downloaded pointer/length (`0x8cbc–0x8cc0`), reads header version at downloaded image `+0x28` (`0x8d50–0x8d78`), and seeds the load context with downloaded name pointer at `[x20+0x98]` and buffer pointer/length at `[x20+0xa0]`/`[x20+0xa8]` (`0x8d84–0x8da0`). It calls load/auth `0x53b50` at `0x8db0`, then (on the successful branch) boots through `0x65708` at `0x8e90`. The ordinary boot path also calls `0x53b50` (`0x9010`) but does not use the same fastboot download seeding.
2. **Previously omitted function `0x53b50` is now covered.** Inside it, `0x545cc–0x54600` checks whether context entries already exist and sets up named image requests via `0x55ad0`. A byte at `[context+0]` chooses different setup branches (`0x5411c–0x54130`, `0x54598–0x545ac`). At `0x55020–0x55040`, when this byte is **zero**, verification flags from `[sp+0x6c]` gain bit `0x4`; when **nonzero** they are passed without that bit. The subsequent call at `0x54794–0x547ac` supplies those flags plus a pointer to a returned component-list handle **to `0x4f0d8`**. The semantics of flag bit 4 and the internal image-acquisition callbacks cannot be assigned from these windows alone.
3. **Decisive table population found:** `0x547b8` checks the pointer returned via the handle. At **`0x54ccc–0x54e04`** the code iterates that returned list: `[list+0x20]` is the element count; `[list+0x18]` points to 24-byte entries with image **name pointer** (`+0`), **buffer pointer** (`+8`) and **byte length** (`+0x10`). A matching requested name is checked by `0x1a8f0` (`0x54d80–0x54d94`); non-duplicates are copied to context entries starting at `[context+0x98]`, and `[context+0x398]` is incremented (`0x54da8–0x54dfc`). This is the producer of entries subsequently read by named-table lookup **`0x66708`**. It conclusively establishes an external component-list **data-flow boundary**, rather than a direct partition-read conclusion from the lookup.
4. **Version-dependent consumers:** the same loader's v3 `vendor_boot` lookup at **`0x66cb8`** and v4 lookup at **`0x66f48`**, plus the DTBO request at **`0x87788`**, consult this component table. In particular, v4 has a conditional `vendor_boot`-not-found path at `0x66f4c–0x66fbc`, with a further conditional recovery/alternate lookup at `0x66fbc–0x67010`. Whether it succeeds when only downloaded boot is preloaded depends on the components `0x4f0d8` actually returns and those later predicates. A named lookup is not itself proof an installed partition is read.
5. **Embedded-DTB legacy path is genuinely reachable downstream:** `0x553d0–0x553f0` passes the chosen image parameters to `0x69570`. At `0x6974c–0x6978c`, `0x69570` reads header version and branches for **0, 1 and 2**, extracting legacy header fields at `0x69790–0x69824`; versions 3 and 4 enter a separate path from `0x69828`. This makes **a self-contained downloaded v2 image with appended DTB technically plausible**, rather than excluded by a generic Motorola-v4 assumption. However `0x4f0d8` validation/source handling and later Motorola DTB selection, board-match/DTBO and FDT memory fixups remain gates to proving it works.
6. **Specific remaining static gap:** implementation of call target **`0x4f0d8`** (outside artifact windows) and the callbacks it invokes. We need the branch that uses a downloaded/preloaded `boot` buffer versus the storage read for `vendor_boot` and `dtbo`; flag `0x4` selection, requested-name list and returned buffer provenance are the deciding values. `0x5bfe8`, which supplies the initial context byte at fastboot `0x8da4–0x8da8`, would additionally be needed if flag-to-mode meaning cannot be resolved from `0x4f0d8`. **Do not request another broad audit or call the missing evidence “the 0x53b50 window.”** That window is verified and analyzed. No separate new static analysis was executed in this correction.

### Actual AArch64 header and placement arithmetic

From the **new** Image: file length **36,436,480**, ARM64 magic `0x644d5241` (`ARMd`), `text_offset=0`, **`image_size=37,158,912`**, flags **`0xa`** (little endian, 4 KiB pages, physical placement); requires a **2 MiB aligned kernel base**. Image header size is **not** the same as file length, and using only file length for collision checks is incorrect.

Reused [exact Motorola MBM disassembly](https://github.com/Drzet/razr2022_nuc/blob/5a8d6ab606c825dbe776db43955c44214f7c64e3/docs/oneli_mbm_kernel_load_address_contract_2026-10-15.md) establishes on the UEFI-variable path `K=KernelBaseAddr+text_offset+O` and `E=KernelBaseAddr+KernelSize+O`. Runtime FDT offset `O`, `KernelBaseAddr`, `KernelSize` and `BaseMemory` remain unknown. With ABL's default 2 MiB DTB allowance, page 4096 and sum of the candidate generic+vendor compressed ramdisks **1,018,709 bytes**, page-rounded **1,019,904 bytes**, the conservative offline nonoverlap condition is:

`E - K >= Image.image_size + align_up(R,4096) + 2 MiB + 8192 = 40,284,160 bytes`.

This checks a **necessary nominal memory budget**, not where Motorola actually places anything. ABL's checked `dtb_address > K` is weaker than `dtb_address >= K+Image.image_size`. The 64-bit fallback `K=BaseMemory | 0x80000` may violate 2 MiB alignment, absent other runtime offsets/relocation. The unpatched native DTB also has a **zero-size /memory entry**, requiring bootloader memory fixups not demonstrated for downloaded v4 boot images. Actual RAM, carveouts, final DTB, ramdisk location and usable UART7 signal are unknown.
