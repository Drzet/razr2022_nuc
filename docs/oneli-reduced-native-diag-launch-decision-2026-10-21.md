### Evidence identity and direct call/data path

Reuse **only** public stock `bootloader.img` SHA256 `bcb596054b276aa3e314412e32b274be8c33b4d93dde9550f55f9a7376496ab3`, Motorola LinuxLoader AArch64 PE SHA256 `5e6db9577a35ec5a5e9c848e271e13048b9ba71a47311d64f0a29b78500eb3ca`, and [research commit `5a8d6ab`](https://github.com/Drzet/razr2022_nuc/commit/5a8d6ab606c825dbe776db43955c44214f7c64e3). Instruction addresses are **PE RVAs**, never load addresses. Existing independently recorded disassembly is in [run 38808611568, artifact 12007666834](https://github.com/Drzet/razr2022_nuc/actions/runs/38808611568/artifacts/12007666834); literal and call-xref snippets in [run 38806852600, artifact 12007090497](https://github.com/Drzet/razr2022_nuc/actions/runs/38806852600/artifacts/12007090497). Both were reused: no new executable analysis output is claimed.

1. **Downloaded boot source:** Motorola fastboot handler `0x8ca8` receives `x1=downloaded-image-pointer` and `w2=downloaded-image-byte-count` (`mov x22,x1`/`mov w21,w2` at `0x8cc0–0x8cc4`), checks the device gate through `0x882c8` at `0x8cfc`, and rejects the blocked branch at `0x8d04–0x8d4c`. It reads the Android `header_version` field at image offset `+0x28` (`0x8d50–0x8d78`); for version **at least 3**, takes the version-dependent `0x8d7c` update. At `0x8d98` it stores the download pointer and count into the load context `[x20+0xa0]` and `[x20+0xa8]`, then calls load/auth `0x53b50` at `0x8db0`. On success it calls `0x65708` at **`0x8e90`** with that same context. The normal boot handler also calls `0x53b50` at `0x900c` and `0x65708` at `0x90b8`, but without the fastboot download-buffer setup: shared downstream parser **does not imply identical source tables**.
2. **Where the downstream parser looks for components:** `0x65708` looks up the selected boot/recovery image in the context via `bl 0x66708` at **`0x65ab8`**, then obtains its `header_version` from the selected header offset `+0x28` and saves the parsed version in its boot context field `+0x3c8` at **`0x65c04–0x65c24`**. Its subsequent calls include `0x66b40` (header/vendor parameters), `0x673d0` (loader address constraints), `0x67918` (boot parameters), and `0x68c78` (DTB/ramdisk relocation).
3. **Exact `vendor_boot` branches:** in `0x66b40`, version == **3** branches from **`0x66c80–0x66c90`** to `0x66708` at **`0x66cb8`** with its `x3` pointing to the `vendor_boot` label (PE string RVA `0xdb063`). Version == **4** branches from **`0x66f10–0x66f20`** to **`0x66f48`** with the same label. Failures have actual strings `Failed to find vendor_boot image` at `0x66cfc` and `vendor_boot image header not found` at `0x66f8c`. Thus *both installed split-v4 boot and vendor_boot are needed for this package*. This proves a named image lookup in the boot context, **not that the fastboot-download path automatically reads `vendor_boot` off storage**.
4. **Exactly what `0x66708` does:** it iterates the context entry table (`[context+0x398]` count, 24-byte entries) at **`0x667c0–0x668c8`**. Each entry contains a name pointer at `+0x98`, image pointer at `+0xa0`, and image size at `+0xa8`, relative to the fixed context/table layout. It compares names through `0x1a8f0` at `0x66864`, and copies the matching pointer and size to the caller at **`0x66884–0x668a8`**. **There is no partition read inside this lookup.** The *producer* that populates `vendor_boot` (and `dtbo`) is upstream, including load/auth `0x53b50`, which is **not disassembled in the retained artifact window**. This is the specific unresolved branch for the downloaded fastboot path, not a blanket unknown about v4.
5. **DTBO choice:** `0x87690` consults parsed boot-header version `+0x3c8`. Its **older header / recovery DTBO** route uses `0x87da0` at `0x87750–0x87764`, whereas the other route looks up a **named `dtbo` image** using `0x66708` at **`0x8776c–0x8778c`**. This again depends on which table entries were supplied. The Motorola DT matching code elsewhere has an *exact-DTB-match / skip-DTBO* branch (logged at `0x6e078`), but it is **not established that the mainline oneli DTB takes that branch**. The accepted mainline `sm8475-motorola-oneli.dts` deliberately contains no Motorola downstream `qcom,board-id`, and its `/memory` size requires a runtime fixup. Stock overlays must not be blindly grafted onto it.
6. **Legacy embedded DTB alternative:** the real ABL `0x69780–0x69824` path recognizes boot header versions **0–2** and reads legacy embedded DTB fields; this is a source-backed **parser branch**, not validation that the fastboot-downloaded v2 path will deliver all components or skip OEM board checks. The Xiaomi v2 recipe is not proof. A self-contained v2 image would also require **repackaging**, excluded by this task.
7. **Memory and ramdisks:** the accepted new uncompressed Image needs `image_size=37,158,912` bytes, 2 MiB-aligned start, and at least **40,284,160 bytes** of nominal kernel-to-DTB reserved span including these ramdisks (see below). The ABL `KernelBaseAddr/KernelSize` query and fallback / `devicetree_space_size` handling are proven by [the pinned placement contract](https://github.com/Drzet/razr2022_nuc/blob/5a8d6ab606c825dbe776db43955c44214f7c64e3/docs/oneli_mbm_kernel_load_address_contract_2026-10-15.md); the actual UEFI values, selected DTBO, memory fixup and ramdisk concatenation can only be observed during a later controlled boot. They are **trial observations**, not a condition that one must have successfully booted in advance.

### Proposed minimal inactive-slot trial and restoration (NOT executable instructions)

1. **Before any write**, establish the actual current active/inactive slot and **installed** build/region from read-only device state (do not infer today's slot from the 2026-10-11 capture). Verify that the bootloader accepts an explicitly targeted inactive-slot write and a **separately recoverable return to the original active slot**. Confirm original stock boot of the active slot still works and the interface can be entered without depending on new Linux. No lock-state probing is part of this offline task.
2. Preserve independently verifiable **stock images and hashes** sufficient to restore the target slot's `boot` and `vendor_boot`, plus provenance of that slot's `dtbo`, `vbmeta`, rollback index and any partition chain relevant to its boot. An exact installed-image dump **or** verified matching stock firmware for that particular slot is required, not just a similar public package. Confirm both target partition capacity limits exceed existing candidate sizes (**37,462,016 boot; 122,880 vendor_boot**) and the restore route can accept exact original images. Do not erase/wipe user data or assume the inactive slot is expendable.
3. At a separately authorized trial, write **only** the two previously verified unsigned v4 candidate images to the *same identified inactive* `boot` and `vendor_boot` logical slots. **Do not modify** stock `dtbo`, `vbmeta`, AVB flags, bootloader, vendor/userdata, or the original active slot. Changes to active-slot selection are a **separate authorized trial action**, not performed here. Do not use a generic `fastboot boot` command for the pair.
4. With a verified independently recoverable bootloader entry, select the trial slot **once**, capture UART7 TX/ground at its measured voltage or an already established equivalent output, and attempt **one** diagnostic boot. Record any ABL vendor_boot/DTB/DTBO selection or rejection, actual FDT memory/board-ID updates, Image alignment/span and presence or absence of `RADIO_EARLY_INSMOD_OK`, `RADIO_EARLY_READY_V1` and `RADIO_EARLY_HOLD`. If a boot failure makes logs unavailable, record exactly where the bootloader stops; do not reinterpret silence as Linux failure. Runtime values are gathered **during** the trial; no prior successful native boot is required.
5. **Rollback:** if rejected, silent or unstable, return to the untouched original active stock slot via the *already verified* independent bootloader/recovery interface. Confirm original Android actually boots, then restore target-slot `boot` and `vendor_boot` **byte-for-byte** from the authenticated stored originals, and restore slot metadata to the recorded original state. If this recovery route cannot be demonstrated before writing, **do not execute the trial**. If the device cannot reach the independent bootloader, stop; recovery beyond that needs a separate approved plan, not further flashes.

**Deciding observations:** a follow-up disassembly restricted to `0x53b50` (especially the context-table record producer for `vendor_boot` and `dtbo`) would settle the downloaded v4 source without any handset write. Until those PE instructions are available, the smallest *device* observation for the chosen writing route is ABL's actual selected DTB/DTBO and its mainline-DTB acceptance when the known pair is loaded. Current fixed images are **offline validated only**. There is no claim of a sanctioned Motorola flashing sequence or guarantee that unsigned images pass the real policy.

### Actual AArch64 header and placement arithmetic

From the **new** Image: file length **36,436,480**, ARM64 magic `0x644d5241` (`ARMd`), `text_offset=0`, **`image_size=37,158,912`**, flags **`0xa`** (little endian, 4 KiB pages, physical placement); requires a **2 MiB aligned kernel base**. Image header size is **not** the same as file length, and using only file length for collision checks is incorrect.

Reused [exact Motorola MBM disassembly](https://github.com/Drzet/razr2022_nuc/blob/5a8d6ab606c825dbe776db43955c44214f7c64e3/docs/oneli_mbm_kernel_load_address_contract_2026-10-15.md) establishes on the UEFI-variable path `K=KernelBaseAddr+text_offset+O` and `E=KernelBaseAddr+KernelSize+O`. Runtime FDT offset `O`, `KernelBaseAddr`, `KernelSize` and `BaseMemory` remain unknown. With ABL's default 2 MiB DTB allowance, page 4096 and sum of the candidate generic+vendor compressed ramdisks **1,018,709 bytes**, page-rounded **1,019,904 bytes**, the conservative offline nonoverlap condition is:

`E - K >= Image.image_size + align_up(R,4096) + 2 MiB + 8192 = 40,284,160 bytes`.

This checks a **necessary nominal memory budget**, not where Motorola actually places anything. ABL's checked `dtb_address > K` is weaker than `dtb_address >= K+Image.image_size`. The 64-bit fallback `K=BaseMemory | 0x80000` may violate 2 MiB alignment, absent other runtime offsets/relocation. The unpatched native DTB also has a **zero-size /memory entry**, requiring bootloader memory fixups not demonstrated for downloaded v4 boot images. Actual RAM, carveouts, final DTB, ramdisk location and usable UART7 signal are unknown.
