### Exact register/data flow and verification flag meaning

1. **Call signature pinned by actual Motorola instruction arguments:** `0x54794–0x547ac` sets `x0=[sp+0x40]` (**AVB operations table**), `x1=x29` (**NULL-terminated requested-partitions array assembled using `0x55ad0` / pointer table at `0xdb378`**), `x2=x25` (**A/B suffix**), `w3=w26` (**verification flags**), `w4=0` (**hashtree mode**), `x5=x22` (**result handle**), and calls `0x4f0d8`. These register roles and `0x4f0d8`'s control flow match the **`avb_slot_verify(AvbOps*, requested_partitions, ab_suffix, flags, hashtree_error_mode, out_data)` ABI**, not a generic Motorola partition-reader routine. The Motorola strings also expose `ops->read_is_device_unlocked` checks. Android's public [libavb API](https://android.googlesource.com/platform/external/avb/+/master/libavb/avb_slot_verify.h) and [ops API](https://android.googlesource.com/platform/external/avb/+/master/libavb/avb_ops.h) are corroborating *semantic comparators*, not a substitute for Motorola callback code.
2. **Flag bit `0x4` is explained, not guessed:** at `0x4f278–0x4f28c`, the compiled verifier checks hashtree mode `w26` and verification-error flag **bit 0** in `w20`; at **`0x4f28c`**, `tbnz w20,#2` diverts execution around top-level vbmeta loading into a requested-partitions processing branch (`0x4f2c8`). The AOSP ABI identifies **bit 0 as `ALLOW_VERIFICATION_ERROR`** and **bit 2 (`0x4`) as `NO_VBMETA_PARTITION`**, under which the regular `vbmeta` partition is not read. This meaning is supported by Motorola's actual conditional topology, but *does not imply no partition reads at all*. In caller `0x55020–0x55040`, `w25 = (context_mode_byte==0) ? ([sp+0x6c]|4) : [sp+0x6c]`, then `0x55b60` tail-calls the verifier with `w3=w25`. Another call at `0x547ac` passes `w26=[sp+0x6c]` without the added bit; these are **distinct paths**. `[sp+0x6c]` is set to Boolean result of an earlier condition (`0x53fcc, 0x5403c–0x54044`), not an arbitrary hardware-measured constant.
3. **Which image buffers are returned:** `0x4f0d8` obtains partition bytes through callbacks in `AvbOps`, potentially preferring preloaded images to storage reads; its main path allocates a result containing named data. `0x547b8` checks the returned result pointer. Caller `0x54ccc–0x54e04` copies each returned **24-byte name / data-pointer / byte-length** record from the result's `+0x18` array and `+0x20` count into the boot context table (`+0x98` entries, `+0x398` count). Later `0x66708` lookups for `boot`, `vendor_boot`, `dtbo` return exactly those records. **Crucial distinction:** bit `0x4` bypasses *normal vbmeta partition authentication*, not necessarily stock `vendor_boot` or DTBO reads. A one-file v4 RAM boot still cannot be equated with the separately packaged v4 pair.
4. **Callback source boundary is exact:** `0x4f0d8` calls through Motorola-specific function pointers in the `AvbOps` table, including `blr` at `0x4f57c`, `0x4f650`, `0x4f86c`; the latter is invoked with a **37-byte GUID buffer**, consistent with AVB's partition-GUID callback. The **registered `read_from_partition` and `get_preloaded_partition` implementations, and their mapping of the downloaded buffer**, are not present in this focused text artifact. The caller obtains `AvbOps*` via **`0x5390c` at `0x54110`**, outside the coverage; this is the smallest source-side registration target to inspect if requested. Therefore **the analysis does NOT prove `vendor_boot`, `dtbo` or even `boot`'s chosen AVB result buffer comes from disk or RAM**. The downloaded `boot` name/pointer/length is *preseeded* in the context at `0x8d84–0x8da0`, but a preseeded context record is not proof AVB doesn't replace it with a storage-returned entry.
5. **Mode is a UEFI protocol result, not a baked-in boolean:** `0x8da4` invokes **`0x5bfe8`** on the downloaded command's name argument; `0x5bfe8–0x5c080` looks up a firmware protocol through an EFI services call via `[...+0x140]` at `0x5c044`, caches it at global `0x107620`, and dispatches its method at **`[protocol+0x10]`** (`0x5c054–0x5c05c`) to return `w0`, which becomes `context[0]` at `0x8da8`. Only its **branch use** at `0x55020` is statically proven; without the protocol's implementation and runtime return value, a fixed `0` or `1` for the Razr may not be asserted. This is a specific **runtime-dependent value** plus a specific missing protocol implementation, not a need for prior Linux boot.

3. **Decisive table population found:** `0x547b8` checks the pointer returned via the handle. ### Actual AArch64 header and placement arithmetic

From the **new** Image: file length **36,436,480**, ARM64 magic `0x644d5241` (`ARMd`), `text_offset=0`, **`image_size=37,158,912`**, flags **`0xa`** (little endian, 4 KiB pages, physical placement); requires a **2 MiB aligned kernel base**. Image header size is **not** the same as file length, and using only file length for collision checks is incorrect.

Reused [exact Motorola MBM disassembly](https://github.com/Drzet/razr2022_nuc/blob/5a8d6ab606c825dbe776db43955c44214f7c64e3/docs/oneli_mbm_kernel_load_address_contract_2026-10-15.md) establishes on the UEFI-variable path `K=KernelBaseAddr+text_offset+O` and `E=KernelBaseAddr+KernelSize+O`. Runtime FDT offset `O`, `KernelBaseAddr`, `KernelSize` and `BaseMemory` remain unknown. With ABL's default 2 MiB DTB allowance, page 4096 and sum of the candidate generic+vendor compressed ramdisks **1,018,709 bytes**, page-rounded **1,019,904 bytes**, the conservative offline nonoverlap condition is:

`E - K >= Image.image_size + align_up(R,4096) + 2 MiB + 8192 = 40,284,160 bytes`.

This checks a **necessary nominal memory budget**, not where Motorola actually places anything. ABL's checked `dtb_address > K` is weaker than `dtb_address >= K+Image.image_size`. The 64-bit fallback `K=BaseMemory | 0x80000` may violate 2 MiB alignment, absent other runtime offsets/relocation.
