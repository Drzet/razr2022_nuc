- Pinned `cape-regulators.dtsi` defines **PMR735A L7E** as RPMh `ldo7`, **2800000..2800000 µV**, `qcom,init-voltage=2800000` (not PM8350 L7B, PM8350C L7C, or PM8350BH). - Motorola comparator drivers confirm *active management*, not permanent enable: `drivers/net/wireless/cnss2/power.c` includes the `wlan-ant-switch` regulator, calling set_voltage/enable during WLAN power-up and disable on teardown; `drivers/bluetooth/btpower.c` includes `qcom,bt-vdd-asd` at 2.8V and does the same for BT. ### Shared Wi-Fi / BT lifetime and source limitations

- Accepted kernel [`drivers/power/sequencing/core.c`](https://github.com/Drzet/linux/blob/2b5acf108ae37040ac1e652e029bb37f5609e886/drivers/power/sequencing/core.c) counts references **on shared dependency units** under a state lock. WCN6855 `wlan` and `bluetooth` targets in [`pwrseq-qcom-wcn.c`](https://github.com/Drzet/linux/blob/2b5acf108ae37040ac1e652e029bb37f5609e886/drivers/power/sequencing/pwrseq-qcom-wcn.c) share `regulators-enable` + clock/XO units; each has distinct GPIO enable unit. Therefore, **when both consumers successfully obtain a pwrseq handle**, stopping Wi-Fi should deassert only WLAN_EN and **retain shared input-rail votes while BT remains active**, and vice versa. Driver source proof, **not actual oneli suspend/coexistence test**. Optional L7E must be added to this common unit, not tied to WLAN-specific or BT-specific shutdown.
- PCI pre-enumeration `pci-pwrctrl-pwrseq.c` uses `wlan` target and matching `vddaon-supply` from an internal PMU regulator child to find the PMU; Bluetooth `hci_qca.c` uses `bluetooth` target from the same PMU when lookup succeeds. **Important fallback:** WCN6855 `hci_qca` currently *silently drops* failed pwrseq handle lookup and attempts legacy direct regulator mode. Hence probe/BT traffic alone cannot prove shared reference ownership; require runtime pwrseq matching + debugfs enable counts and paired on/off tests. Do not install a separate GPIO81 BT_EN consumer when the common PMU owns it.
- Upstream generic WCN6855 pwrseq **does not use `swctrl-gpios` (TLMM82)** despite the generic binding allowing the property; vendor BT `btpower.c` treats its switch control as input/state. Pinmux/installed semantics belong to Wireless; **no control GPIO duplication or new supply inference** is justified. PMU GPIO80 WLAN_EN, GPIO81 BT_EN and GPIO204 XO remain owned by the one PMU provider in the source proposal.
- `regulator_bulk_enable` shared references do **not establish system-sleep retention**. PM8350/PM8350C RPMh driver issues active-only state requests; no oneli runtime wake/RPMh sleep contract exists. Successful generic sequencing does not prove coexistence, RF calibration, BT firmware/transport or power integrity. Check Wi-Fi-only, BT-only, both-on, each-off-in-turn, failed second-enable/unwind, and suspend/resume with hardware once available.

- **Recommendation:** keep the existing PTN3222 **3.075–3.300V** voltage request unchanged. Its **3.080V** selectable output is **8mV (0.26%)** above the original **3.072V** initial vote. That tiny grid-rounding difference is **not a USB/DP development or board-integration blocker**, and it does not justify modifying regulator rounding or lowering the PTN minimum. Published NXP **CUK** Rev1.2 VDD3V3 range is 2.85–3.63V ([NXP PDF](https://www.nxp.com/docs/en/data-sheet/PTN3222_CUK.pdf), table31) and WILLSEMI WAS7227Q accepts 2.5–5.5V ([original datasheet](https://www.omnivision-group.com/files/product/files/WAS7227Q_V1.4.pdf)). - Even the stock BOB 3.296V and S1C 1.880V *initial votes* are not exact selectable points with present mainline PMIC5 maps: BOB 3.000V + 0.032Vn → nearest **3.288/3.320V**, S1C 0.320V + 0.016Vn → nearest **1.872/1.888V**.
