## Iris field-by-field resource/loader disposition

Dedicated [stock-vs-Iris and loader requirement report](../vpu/2026-10-12-iris-resource-loader-contract.md) grounded in base FDT `/soc/qcom,vidc@aa00000` and pinned kernel `iris_firmware.c`, `iris_probe.c`, `iris_resources.c`, `mdt_loader.c`.

**Confirmed stock properties:** MMIO `0x0aa00000 + 0xf0000`, IRQ174, PAS9, `vidc,firmware-name="vpu20_4v"`, no-map video carveout `0x9fd00000+0x700000`. Signed reference VPU `vpu20_4v.mbn` ELF32 physical PT_LOAD span rounds to **0x700000**, fitting this reservation. Two nonsecure SMMU child context banks SIDs **0x2180** (bitstream) and **0x2187** (pixel), both flag `0x400`, distinct IOVA starts `0x25800000` and `0x00100000`, common end `0xe0000000`. Proposed Iris `dma_mask=0xe0000000-1` is now **source-supported as upper ceiling**, **not** proof of correct upstream device-level two-domain setup.

Four exact allowed clock rates: 239999999, 338000000, 366000000, 444000000 Hz. Three **stock ICC** paths CNOC/DDR/LLCC; current Iris RFC only requests **two** and does not vote LLC. Two VIDEOCC GDSC supplies observed; mainline Iris requires four named power/OPP domains and exact required-opps not present in standalone vendor VPU node. **Remaining integration blockers:** nonsecure SMMU attachment translation, RPMh OPP/corners, three-path ICC/LLCC runtime votes and calibrated bandwidth policy. These are not cured by recovered firmware names. GPU's shared UBWC review accepts static v4 HBB16 match as [INFERRED] platform default pending real SMEM HBB.

**Linux loader exact requirements:** stock Android ext4 `image/vpu20_4v.mbn` (2,024,040B SHA256 `9582ea4c5565408bd3e5ba6f8fffc7881f226cae001b6fcd7a0c868de9add9af`) does not automatically live in Linux firmware search path. SM8475 descriptor has no default fwname; missing `firmware-name` DT returns -ENOENT. Boot-owned eventual disabled node could explicitly name `qcom/vpu/vpu20_4v.mbn`, if Debian installs same reference signed MBN at `/lib/firmware/qcom/vpu/vpu20_4v.mbn`, but this is a **proposed install layout** not executed or authenticated. Alternate signed split `vpu20_4v.mdt` (5404B) **requires** all correctly phdr-indexed `vpu20_4v.bXX` files alongside it; loader substitutes `b%02d` program-header index and does not concatenate arbitrary split files. `qcom_mdt_load` and `qcom_pas_auth_and_reset(9)` remain untested with reference bytes on phone. Gen2 descriptor is statically selected on this candidate; video-firmware.2.4 version does **not** prove HFI compatibility.

Kernel branch only changed comments at `869cf4a6ad21afcc2435c4e2d1d4fa9ab33fb4bf` correcting obsolete “firmware not inspected” claim and warning that three ICC/two SMMU contexts are not implemented equivalently. It changes no executable code or bindings. **No new full kernel build was run because that gate is unchanged and previously passed.**
