## Changes and provenance

The pinned Motorola [cape-gpu.dtsi](https://github.com/MotorolaMobilityLLC/kernel-devicetree/blob/90fa7be1db5bd47202673d4431408659149a7359/qcom/cape-gpu.dtsi#L4-L29) declares `qcom,gpu-model = "Adreno730v3"` and **`qcom,chipid = <0x07030002>`**. The SoC `cape.dtsi` includes this file. The baseline's [`a6xx_catalog.c`](https://github.com/Drzet/linux/blob/a5ebb76233b79db01e82e061173cb73c6d2b5c6b/drivers/gpu/drm/msm/adreno/a6xx_catalog.c#L1480-L1503) recognises **only `0x07030001`** for A730. [`adreno_device.c`](https://github.com/Drzet/linux/blob/a5ebb76233b79db01e82e061173cb73c6d2b5c6b/drivers/gpu/drm/msm/adreno/adreno_device.c#L49-L65) checks exact IDs; `qcom,adreno-730.2` maps to `0x07030002` through `find_chipid()`.

Kernel patch `4955f07a94ea3c51e423e34d819ac3f76f1c9d37` adds the `0x07030002` ID to the existing A730 catalog record. [INFERRED] Using the existing A730/GMU power-up configuration and firmware is the least invasive starting point, but compatibility with the A730v3 variant is not proven by identification alone. This is a candidate requiring validation, not a claim of a working GPU.

Already present at the pinned baseline:

- `drivers/clk/qcom/gpucc-sm8450.c`: exact `qcom,sm8475-gpucc` match, with SM8475-specific Lucid OLE PLL setup in `gpu_cc_sm8450_probe()`. No replacement clock driver is needed.
- `Documentation/devicetree/bindings/display/msm/{gpu,gmu}.yaml`: GPU/GMU binding supports the inherited `qcom,adreno-gmu-730.1` node, clocks, power domains and OPPs.
- [Baseline `sm8450.dtsi`](https://github.com/Drzet/linux/blob/a5ebb76233b79db01e82e061173cb73c6d2b5c6b/arch/arm64/boot/dts/qcom/sm8450.dtsi#L2427-L2567): GPU, GMU, SMMU, GPUCC and reserved `gpu_micro_code_mem` nodes; GPU/GMU disabled pending board support. ## OPP merging defect: confirmed resolution for Boot

The baseline SM8450 GPU OPP children contain **12** rates (MHz): `818, 791, 734, 640, 599, 545, 492, 421, 350, 317, 285, 220`. [Community `sm8475.dtsi` at `bf1d29fced6e156dd6090a9b6600a8c44259c114`](https://github.com/sm8450-mainline/linux/blob/bf1d29fced6e156dd6090a9b6600a8c44259c114/arch/arm64/boot/dts/qcom/sm8475.dtsi#L59-L115) adds **13** rates (MHz): `900, 862, 815, 765, 710, 645, 580, 515, 439, 364, 324, 285, 220`. Two children (285 and 220) share node names, so copying only this override leaves **23 distinct OPP children**, ten of them inappropriate SM8450-only levels. Motorola [`cape-gpu.dtsi` powerlevels](https://github.com/MotorolaMobilityLLC/kernel-devicetree/blob/90fa7be1db5bd47202673d4431408659149a7359/qcom/cape-gpu.dtsi#L67-L245) independently corroborate all thirteen frequencies and GPU `qcom,level` values.

**Proposed shared `sm8475.dtsi` change, to be applied by Boot, not the GPU branch:** retain the inherited `gpu_opp_table` label and phandle, explicitly delete the **ten** SM8450-only child nodes, and add/override all thirteen SM8475 nodes. ## Firmware inventory and provenance requirements

The A730 entry in the pinned catalog requests:
1. `qcom/a730_sqe.fw` (SQE), using the kernel's `qcom/` first-search path.
2. `qcom/gmu_gen70000.bin` (GMU), same lookup.
3. Signed zap shader by `zap-shader/firmware-name` in the board DT. The catalog's fallback is `a730_zap.mdt`, **not** proof that this is the right signed Motorola image.

Both SQE and GMU blobs are present in [linux-firmware `qcom/`](https://kernel.googlesource.com/pub/scm/linux/kernel/git/firmware/linux-firmware/+/refs/heads/main/qcom/) and documented in its WHENCE as SQE **v1.81** and GMU **v4.00.07** ([firmware provenance commit `42e9d5a5994cf8178558cc2f8d9733e0dedddc0c`](https://git.powerel.org/kernel/linux-firmware/commit/42e9d5a5994cf8178558cc2f8d9733e0dedddc0c)). A generic `qcom/sm8450/a730_zap.mbn` exists; the community Nothing Pong board selects `qcom/sm8475/nothing/pong/a730_zap.mbn`. **Neither is validated as the signed blob for Motorola oneli.** The correct oneli path, availability, hash, signature acceptance and any MDT segments remain **unknown**. Do not invent a path, ship another board's image as tested, or commit proprietary blobs into this repository. Extract/provenance-check from the actual phone's existing firmware, record source partition/build/hash and device board revision, then set `firmware-name` to the verified path.

The kernel's `adreno_gpu.c` supports board-specific `zap-shader/firmware-name` with direct firmware request and secure-world authorization. No measured runtime success exists.

## Reviewed kernel configuration

From baseline Kconfig: `CONFIG_DRM_MSM` enables MSM DRM and Adreno; `CONFIG_SM_GCC_8450` and `CONFIG_SM_GPUCC_8450` enable existing SM8475-matching clock controllers; `CONFIG_QCOM_RPMH`, `CONFIG_QCOM_RPMHPD` provide downstream power/level infrastructure; `CONFIG_ARM_SMMU` and `CONFIG_QCOM_AOSS_QMP` must be reviewed with overall Boot configuration. `CONFIG_DRM_MSM_DPU`/`CONFIG_DRM_MSM_DP` are display integration choices, **not prerequisites for proving render-node GPU command submission**. The baseline ARM64 `defconfig` sets `CONFIG_DRM_MSM=m`; actual final resolved config, built-in/module ordering and initramfs contents have not been recorded. For initial initramfs bring-up, GPUCC and MSM should be available at boot or accompanied by correct modules and firmware.

## Validation

**Source-checked:** Motorola chip ID and levels, exact upstream catalog miss, SM8475 clock compatibility, SM8450 OPP leftovers and independent firmware names.

**Not run:** `dtc`, `dtbs_check`, kernel/DTB compile, module load, device boot, GPU command submission, thermal or performance measurements. No build/toolchain/device firmware results are asserted.

Proposed acceptance stages:
1. **Build:** pin exact Boot/GPU/integration SHAs and compiler. Build ARM64 kernel and affected oneli DTB; run binding validation. Decompiled DTB must contain *exactly 13* GPU OPP nodes at the listed MHz, `compatible = "qcom,adreno-730.2", "qcom,adreno"`, `qcom,sm8475-gpucc`, and the reviewed firmware-name; confirm no SM8450-only OPPs. Preserve commands, logs and generated config in `tests/templates/build-record.md`.
2. **Firmware + probe:** on the physical oneli record installed build, board revision, the *actual* SQE/GMU/zap paths and SHA256; boot with GPU enabled. Check DRM/GMU firmware version, power-domain probes, `dmesg`, absence of firmware errors, failed GMU HFI, GPU hangs, IOMMU faults and that a `/dev/dri/renderD*` node exists. Do not count merely creating a DRM card as acceleration.
3. **Headless rendering first:** use compatible Mesa Freedreno (OpenGL/GLES through EGL) and optionally Turnip (Vulkan). Capture `eglinfo` and `vulkaninfo --summary` with software fallback ruled out, then execute an offscreen render, verify readback/checksum, exercise repeated allocations/submissions/synchronization and record CPU/GPU faults. Record exact Mesa version and driver name; do not infer acceleration from the presence of a render node.
4. **Display path later:** when DisplayPort or DSI KMS is integrated, run a KMS/GLES test (e.g. `kmscube`) on a confirmed connector and verify flipping/page presentation, suspend/resume, repeated GPU idle/wake transitions, all exposed clock steps, thermal throttling and overnight stability.
