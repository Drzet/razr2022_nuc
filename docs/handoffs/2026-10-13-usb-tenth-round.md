### Evidence gates and smallest prospective adaptation

**Source-resolvable gates:** obtain attributable oneli BOM/schematic or identified-part documentation tying the populated part/revision to this address, GPIO7 function/polarity and allowed power/reset timing. Match the three override registers and normal/host values to that revision's documented writable fields. Resolve S10B/L2B parents, voltage constraints and required enable order with Power/Boot. Existing DT family strings, matching register names, and other boards' active-low reset do not settle those questions. The published NXP datasheets linked in the historical RFC are candidate-family documentation, not evidence of a 2022 handset's populated revision.

**Hardware-only confirmation when the phone returns:** establish effective installed DT/overlay; after verified rail/reset setup, record read-only revision/chip identification with exact stock/software context and compare to the identified part's documentation. Confirm electrical reset/settle and power sequencing, normal/device and host enumeration, disconnect/reconnect and retained bus suspend/wake. No handset access or native Linux result exists for this assignment; the later failed ADB session does not invalidate 2026-10-11 evidence.

**Conditional minimal delta, requiring a new coordinator assignment:** if PTN3222 identity and register semantics are established, USB should adapt **`drivers/phy/phy-nxp-ptn3222.c`** and its binding, retaining its generic PHY interface and authorship. Reuse community regmap setup/checked-write unwind; choose a maintainer-reviewed semantic tuning interface or identified variant/board profile instead of exposing Android raw-register arrays. Add only the required normal/host profile selection through `.set_mode`, cache role while unpowered, and replay the selected profile after power/reset and on powered role changes. Handle mode-before-init and init-before-mode; do not publish a successful programmed state after a failed write. Add reset delay or explicit rail sequencing only if required by the identified part/board. Existing SNPS role forwarding supplies the interface; no consumer rewrite is selected. If identity proves a different part, return to coordinator for a compatible/reuse decision before proposing code.

**Owners and focused future validation:** USB owns provider/binding; Boot alone owns eventual board/SoC `phys`, GPIO and supply phandles; Power confirms electrical parents/constraints; coordinator approves implementation and integration. Before implementation, agree those contracts. A future changed provider requires production-function fault tests for read/write failure at each profile position, original-error preservation, reset/rail unwind, provider defer and reprobe, both role-orderings and reset/replay. Binding tests must use actual valid/invalid instances, rejecting unsupported/raw properties; compile/link changed provider and consumer only when code exists. Hardware enumeration and wake remain separate acceptance gates. No tests or builds are needed for this documentation-only decision.
