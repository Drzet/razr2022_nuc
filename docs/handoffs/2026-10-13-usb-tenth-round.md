## Register identity: supported constants, BUK hold

The retained [candidate provider at 61202a82](https://github.com/Drzet/linux/blob/61202a82ad004302fcc04e321075e190f00b29ed/drivers/phy/phy-nxp-ptn3222.c) checks identity only for the experimental `nxp,usb2-tuning-profile = "motorola,oneli"` profile. After ordered supply votes, reset release and a 1000–1500 us wait, it reads **0x13**, then **0x14, 0x15, 0x16** individually, checking each read error. It assembles `id = reg14 | (reg15 << 8) | (reg16 << 16)` and accepts only the full 24-bit constants below. Revision is logged, not compared. Unknown ID returns **-ENODEV from PHY init before tuning**, asserts reset and enters the existing tracked cleanup/retry path. This is an init-time compatibility gate, not an I2C probe-time identification guarantee. Profile-absent legacy operation does not perform this check.

| Attributable NXP source, checked 2026-10-15 | 0x13 revision | 0x14 / 0x15 / 0x16 | Candidate match |
| --- | --- | --- | --- |
| [PTN3222_CUK.pdf](https://www.nxp.com/docs/en/data-sheet/PTN3222_CUK.pdf), **Rev1.2, 11 August 2023**, Table9 p12; Tables26–29 pp21–22 | 0xa2 | 0x22 / 0x32 / 0x02 | `PTN3222_CHIP_ID_CUK = 0x023222` |
| [PTN3222HUK.pdf](https://www.nxp.com/docs/en/data-sheet/PTN3222HUK.pdf), **Rev2.0, 6 May 2026**, Table8 p17; Tables25–28 pp27–28 | 0xa4 | 0x22 / 0x32 / 0x01 | `PTN3222_CHIP_ID_HUK = 0x013222` |
| **PTN3222BUK**, schematic exact-part identity | **Not established** | **Not established** | No supported BUK match or mismatch determination |

Both public register descriptions separate silicon revision at 0x13 from the configuration/chip-type fields at 0x16. A common `0x3222` pair alone does not establish revision, configuration, package or full-match compatibility. Conversely, the BUK suffix does not prove a different ID. The CUK ordering table names CUK/GM, not a BUK mapping. The source constant names do not prevent a BUK from matching either numeric tuple if exact-part evidence later supports it.

**Motorola coverage:** pinned [kernel-msm `0450c5076a8ec9415a10888c8c183ef6ff5f91b8`, repeater-i2c-eusb2.c](https://github.com/MotorolaMobilityLLC/kernel-msm/blob/0450c5076a8ec9415a10888c8c183ef6ff5f91b8/drivers/usb/repeater/repeater-i2c-eusb2.c) uses family compatible `nxp,eusb2-repeater`. It defines chip-ID addresses but its NXP init reads only REVISION_ID (0x13), ignores the read return value and logs the result. It never checks 0x14–0x16. Source blob **`08dc35f0eac2d597a402ee25bfc37035035ac638`**, retained source SHA256 **`09fa3973800e1d7259c75805ad47dab843bc23d65fdb448384554a0f5cd68b69`**. Neither this implementation nor the existing stock DT/ADB record supplies the missing BUK bytes; vendor absence of a rejection check is not evidence that our stricter check passes.

**Focused retrieval boundary:** searched exact BUK identity/register terms, including `PTN3222BUK CHIP_ID`, `REVISION_ID`, `0x14`, `023222`, and NXP exact-part documentation. NXP HUK Rev2.0 references **AN13637**, a BUK abnormal-EOP-pulse application note dated 2022 (section16 p49); this establishes a named BUK-specific source lead, not its ID table or a required workaround. Direct web retrieval of `PTN3222BUK.pdf`, generic `PTN3222.pdf` and `AN13637.pdf` did not yield inspectable documents through the tool. This is a bounded negative retrieval result, not proof those documents do not exist or require restricted access. No attributable exact-BUK ID specification was found in the inspected sources. The earlier pinned upstream/pending/community reuse research remains in the [adaptation handoff](https://github.com/Drzet/razr2022_nuc/blob/2b64829bd78478a89e18d5bd50952f7a72e3f0c5/docs/handoffs/2026-10-13-usb-tenth-round.md); no broad audit was reopened.

**Exact missing datum / release condition:** obtain either (a) an attributable **PTN3222BUK** register specification/erratum, with document revision and explicit 0x13–0x16 mapping; or (b) a **read-only identity capture** of bytes **0x13, 0x14, 0x15, 0x16**, each with its read return status, at **7-bit address 0x4f** on an identified oneli board under a known stock-powered, reset-released state. Record board/firmware/bus identity, timing/state and raw bytes without inferring the package from the bytes alone. Read-only means no register-content writes or power/reset experiments; ordinary addressed I2C reads may still transmit the register address. Hardware is unavailable and this capture was not attempted. A tuple equal to either accepted value establishes that the current numeric gate passes on that observed board, not complete BUK electrical/timing/errata qualification. Any different value requires exact-part attribution and review before changing the allowlist. Do not invent a BUK constant, mask off 0x16, substitute a revision guess or globally bypass rejection.

## Reset: reference-schematic contract resolved

The pinned [Motorola DT `90fa7be1db5bd47202673d4431408659149a7359`, cape-moto-common-overlay-base.dtsi](https://github.com/MotorolaMobilityLLC/kernel-devicetree/blob/90fa7be1db5bd47202673d4431408659149a7359/qcom/cape-moto-common-overlay-base.dtsi#L127) declares singular `reset-gpio = <&pm8350c_gpios 7 GPIO_ACTIVE_HIGH>`. In the pinned vendor driver, `eusb2_repeater_reset(ur, bring_out_of_reset)` directly passes that boolean to `gpiod_set_value_cansleep()`. The [same-revision SNPS consumer](https://github.com/MotorolaMobilityLLC/kernel-msm/blob/0450c5076a8ec9415a10888c8c183ef6ff5f91b8/drivers/usb/phy/phy-msm-snps-eusb2.c#L667) powers up, calls reset(true), then initializes; its ordinary disconnect calls reset(false) before powerdown. Thus vendor **true means physical high / release**, false means physical low / assert. Its debug words print the inverse assertion description and are not the electrical contract. Vendor `GPIOD_OUT_HIGH` initially requests physical high with that active-high flag.

Linux's [GPIO consumer semantics at baseline a5ebb762](https://github.com/Drzet/linux/blob/a5ebb76233b79db01e82e061173cb73c6d2b5c6b/Documentation/driver-api/gpio/consumer.rst#L261) define descriptor values as logical assertion. The upstream-style provider obtains `GPIOD_OUT_HIGH`, uses logical **0** on init to deassert reset, and logical **1** for abort/exit. For the direct schematic RST_N connection, the required future descriptor is:

`reset-gpios = <&pm8350c_gpios 7 GPIO_ACTIVE_LOW>;`

| Candidate action with active-low descriptor | Logical value | Physical RST_N | Meaning |
| --- | --- | --- | --- |
| Probe `GPIOD_OUT_HIGH` | 1 | Low | Reset asserted |
| Init after supplies are enabled | 0 | High | Reset released |
| Abort / exit before supply cleanup | 1 | Low | Reset asserted |

**No inversion of the candidate's calls is required.** Copying vendor flag0 into this descriptor would invert those physical actions. Retain plural upstream `reset-gpios`; do not port the vendor callback convention or its debug text.

**Provider numbering:** physical **PM8350C GPIO7** is DT cell **7**, pinctrl name **`gpio7`**, chip-local zero-based offset **6**. Baseline [pinctrl-spmi-gpio.c](https://github.com/Drzet/linux/blob/a5ebb76233b79db01e82e061173cb73c6d2b5c6b/drivers/pinctrl/qcom/pinctrl-spmi-gpio.c#L794) copies the second-cell flags and subtracts `PMIC_GPIO_PHYSICAL_OFFSET = 1` from the first cell. The [PMIC GPIO binding](https://github.com/Drzet/linux/blob/a5ebb76233b79db01e82e061173cb73c6d2b5c6b/Documentation/devicetree/bindings/pinctrl/qcom,pmic-gpio.yaml#L117) uses two cells. Do not put 6 in the DT specifier, use a dynamically assigned global GPIO number, or substitute TLMM7 / PM8350BH. The label is the vendor provider spelling; Boot must use its actual PM8350C controller label and review mux, ownership, power source and pin configuration before staging a node. Descriptor polarity alone does not prove the powered pin's waveform, reset pulse width, rail-to-reset timing or installed-board wiring.

## Supplies, tuning and minimal proposal

Reuse [stock PVT/DT evidence](../usb_stock_pvt_variant_ps5169_2026-10-12.md) and the new reference schematic. Proposed binding endpoints remain **`vdd1v8-supply` → PM8350 S10B**, **`vdd3v3-supply` → PM8350 L2B**. The pin name VDD3V3 does not turn the schematic's nominal **3.07 V** rail into a measured 3.3 V source. Existing Motorola nominal init is **3.072 V** within its declared **2.7–3.3 V** range; candidate requests **3.075–3.3 V**, with **1.8 V** on S10B; load votes are **3.5 mA for L2B** and **32 mA for S10B**. The schematic label is rounded nominal evidence, not proof of regulator selection/readback. Review the actual L2B constraints/provider rounding before eventual integration; do not silently widen the candidate voltage range or claim the two numerical settings are identical.

The retained profile enables **1.8 V first, then L2B**, releases reset, checks identity, then writes **0x06=0x40, 0x07=0x22, 0x08=0x64** for device/OTG or **0x08=0x24** for host, followed by its existing 500–1000 us configuration wait. Teardown asserts reset before reverse supply cleanup. These remain the accepted source/host implementation, not measured physical sequencing or new BUK timing qualification. The existing generic-PHY provider (`#phy-cells = <0>`) and SNPS consumer interface remain unchanged; no vendor repeater framework or arbitrary raw-register DT ABI is proposed.

**Minimal proposal for a later explicitly selected change:** use the existing plural reset property with the active-low PM8350C GPIO7 descriptor above; retain the generic PHY interface and known supply endpoints. **No provider reset-call patch is needed.** Hold BUK-specific ID/binding selection pending the named identity evidence; do not assign a CUK/HUK compatible to BUK from matching register patterns alone, invent a BUK compatible, or broaden the allowlist in this task. If a future reviewed BUK binding is needed, document its actual register/timing compatibility and fallback rules first. Boot owns all shared DTS and Power/Boot own rail-provider/parent reconciliation. New schematic parent facts are linked in the fixed evidence record; no regulator enablement or duplicate parent-tree implementation is part of this USB decision.
