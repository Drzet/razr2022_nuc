## Exact evidence and new binary inspection

The accepted kernel is Drzet/linux commit 2b5acf108ae37040ac1e652e029bb37f5609e886, release 7.3.0-rc6-g2b5acf108ae3. Inspected the real Image from immutable combined artifact 11768562884, after SHA256 verification (Image 3a8fa9620e0fc8de68ce8db45dacdfd811a2ba2c9718f9cddee3893ec9af0939).

The 64-byte ARM64 Image header has magic 0x644d5241 (ARM\\x64), text_offset=0, image_size=53,215,232 (0x32c0000), flags=0xa (LE, 4KiB pages, flexible physical placement enabled), res2/res3/res4=0 and res5=64 (PE/COFF offset). The actual Image file is 52,369,920 (0x31f1a00) bytes. Its **effective allocation is 845,312 bytes larger** than the file. A PE header offset does not show that Motorola uses EFI.

The exact [pinned ARM64 boot protocol](https://github.com/Drzet/linux/blob/2b5acf108ae37040ac1e652e029bb37f5609e886/Documentation/arch/arm64/booting.rst) and [Image header definitions](https://github.com/Drzet/linux/blob/2b5acf108ae37040ac1e652e029bb37f5609e886/arch/arm64/include/asm/image.h) specify a 2MiB-aligned base plus text_offset, at least image_size bytes available at the Image start, a DTB on an 8-byte boundary no larger than 2MiB, and an initrd fully within a suitable 1GiB-aligned physical window up to 32GiB covering the Image. The loader also supplies x0=physical FDT address and initializes memory, CPU and cache conditions.

Direct compiled-DTB structural-token inspection of accepted sm8475-motorola-oneli.dtb (SHA256 d3c9abcea9950200babbcf6c979073dc94c6af5cac68578540ad570db4a14a03) found 898 nodes and 3,418 properties: /memory@a0000000/reg has 64-bit base 0xa0000000 **and size zero**, so a firmware-supplied RAM map/change is required. /chosen/stdout-path is serial0:115200n8; alias serial0 resolves to /soc@0/geniqup@9c0000/serial@99c000, enabled. No /chosen/bootargs, /__symbols__ or /__fixups__ node exists. DTB file is 104,726 bytes. These are binary observations, not bootloader-selection evidence.

Public Motorola Android 14 reference boot and vendor_boot headers are v4. From configs/oneli-boot-packaging-v2.json and pinned VPU focused metadata: boot image kernel payload 46,854,172 B, generic ramdisk 1,380,093 B, boot-v4 signature 4,096 B, OS version 402653593, empty boot cmdline. Vendor boot contains legacy-LZ4 vendor ramdisk, two unpadded stock MSM530/MSM540 base FDTs, one type-1 fragment and 85 B bootconfig. PVT index-3 stock overlay (board ID 0x45/c000) is a reference *candidate*, not observed runtime selection. The [actual stock phone capture](oneli_stock_android14_adb_hardware_capture_2026-10-11.md) establishes PVT 0xC000, MBM-3.0-oneli-c66ed235df0-250923-U2SLS34.1-42-14-11-e37c37, active slot _a during that session, independent boot/vendor_boot/dtbo/recovery/vbmeta partitions in A and B, but **not their bytes or contents**.

## First controlled experiment: prerequisite-only sequence

1. **Read-only inventory:** actual current and other-slot state (active, bootable, successful flags), partition sizes, exact installed stock image hashes for both relevant slots, source-matched OEM originals, and bootloader command capability for complete boot/vendor_boot/DT inputs. Previous physical ADB establishes partition *names*, not hashes or a proven recovery image. Owner-managed unlock is not an offline blocker.
2. **Restoration first:** verify a genuinely working recovery/bootloader entry path and a coherent restore set covering whichever boot/vendor_boot/dtbo/vbmeta partitions could be changed. An unused slot is not a verified spare. Do not assume RAM-only boot can replace vendor_boot or all DT inputs.
3. **Output path first:** prove accessible physical UART RX/TX reference and voltage (or a tested equivalent early-log path), then confirm TX at the relevant phase. DTS pinctrl names do not prove accessible board pads.
4. **Native handoff:** resolve OEM image acceptance, populated memory DTB, overlap-free physical placement, DTBO choice, actual command-line supply, bootconfig, AVB/recovery policy. If any gate remains unresolved, **STOP: device evidence required**. No executable flashing commands, no image mutation, no acceptance for phone use.

AOSP/public documented behavior is separated above from *actual MBM behavior*. No attributable public Motorola MBM loading implementation or disassembly that determines its address and DT handling has been established. A PE header, an AOSP pack/unpack success and a generic fastboot command list do not substitute for the exact OEM loader.

The seventh-round Userspace console error-body fix is independent. Consume a new diagnostic payload only after its changed bytes, new hashes and real diskless test are published. Preserve accepted v1 and run 38310449244 unchanged. Do not initiate a duplicate kernel/QEMU/packaging run or ROM scan.
