# Oneli Iris2 nonsecure DMA ownership: eighth-round bounded decision

**2026-10-13, source-only design decision.** Assignment: [eighth review](https://github.com/Drzet/razr2022_nuc/blob/main/docs/EIGHTH_REVIEW.md) (blob `900d9be2788fb402a1564a03dd5fd31a36917bf3`), [NEXT_TASKS](https://github.com/Drzet/razr2022_nuc/blob/main/docs/NEXT_TASKS.md) (blob `03f1e2c0e72f76fb7fb62d1a18e6ab7f63705339`). Existing [VPU sixth-round decision](2026-10-12-bounded-resource-translation-decisions.md) accepted. No firmware/stock extraction, new binding, driver code, CI rebuild, or device experiment in this round.

## Recommendation

**Design for two real, separately DMA-attached nonsecure consumer devices: one bitstream/nonpixel DMA context for stream `0x2180/0x400` and one pixel DMA context for `0x2187/0x400`.** Keep the control/register/SCM firmware-loader platform device separate from both data DMA owners, and route each allocation/attach/map/unmap/free through its selected DMA device.

This is the **only currently source-faithful architecture proposal**, not yet an implementation authorization. The compiled reference stock DT supports two separate nonsecure context nodes. The pinned Waipio downstream driver actually uses **two different `struct device *` DMA attachment targets**, selected by buffer region. Upstream Linux's normal per-device DMA/IOMMU APIs support that ownership pattern without guessed auxiliary domains. The split is **not automatically a security boundary** between the two nonsecure classes. No proof yet of equivalent single-domain HFI/MMU behavior or of Motorola's exact runtime selected overlay.

**Decision at present:** keep experimental Iris disabled. A future isolated disabled prototype can be designed with child platform devices and a reviewed binding, but **do not commit an active two-context DTS or assume it passes** until the exact child-device binding, pool limits, probe sequencing and failure behavior are justified and validated. No dependency on accepted kernel `Drzet/linux:razr/integration` `2b5acf108ae37040ac1e652e029bb37f5609e886` or its diagnostic host artifacts.

## Downstream path, buffer ownership and exact role selection

In [`msm_vidc_driver.c::msm_vidc_get_buffer_region` lines 949–1026](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_driver.c#L949-L1026), **nonsecure decode** chooses:

| Buffer type | Selected nonsecure region | Source role |
| --- | --- | --- |
| Decoder compressed V4L2 input | `MSM_VIDC_NON_SECURE` / `venus_ns` | Bitstream |
| Decoder raw V4L2 output, DPB, VPSS | `MSM_VIDC_NON_SECURE_PIXEL` / `venus_ns_pixel` | Pixel |
| Input/output metadata; BIN, COMV, NON_COMV, LINE, PERSIST | `MSM_VIDC_NON_SECURE` / `venus_ns` | Nonpixel/internal |
| Nonsecure encoder input / output | Pixel / nonpixel respectively | Reverse external queue roles |

**Secure sessions are different and explicitly out of this task**: distinct secure pixel, nonpixel and bitstream context banks/heaps and `mem_buf_lend` VMID permissions are involved. The downstream nonsecure/nonsecure-pixel distinction does **not** prove separate trusted-world security privilege; `is_non_secure_buffer` rejects secure DMA-bufs in *either* nonsecure region. Exclude secure sessions from any future nonsecure-only prototype and fail them explicitly.

[Downstream `msm_vidc_probe.c` lines 476–528](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_probe.c#L476-L528) uses `of_platform_populate` on VPU child devices with compatible `qcom,msm-vidc,context-bank`; `msm_vidc_read_context_bank_resources_from_dt` -> `msm_vidc_populate_context_bank` -> `msm_vidc_setup_context_bank` reads `label`, `virtual-addr-pool`, secure/coherency state, takes **the child's** `struct device *`, checks `iommu_get_domain_for_dev(cb->dev)`, and associates the region with that child (see [`msm_vidc_dt.c` lines 774–919](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_dt.c#L774-L919)). **The logged vendor pool is not itself a proof that the generic DMA allocator enforces the same lower IOVA bound.**

### User / externally allocated DMABUF path

`msm_vidc_get_driver_buf` and `msm_vidc_map_driver_buf` ([`msm_vidc_driver.c` lines 2790–2909](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_driver.c#L2790-L2909)) take a tracked dmabuf, obtain a **buffer-type-specific** region via the platform callback, then map it. For decoder CAPTURE/OUTPUT pixel buffers they intentionally take a second mapping ref for **delayed unmap** (read-only-reference-buffer / display lifetime). `msm_vidc_memory_get_dmabuf` holds one strong reference per tracked imported dmabuf (incrementing a logical ref on reuse).

[`msm_vidc_memory.c::msm_vidc_memory_map` lines 177–280](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_memory.c#L177-L280) chooses `get_context_bank(core,map->region)` then `dma_buf_attach(dmabuf, cb->dev)`, `dma_buf_map_attachment` (DMA_BIDIRECTIONAL), consumes `sgt->sgl->dma_address`, retains **attachment, table, address, region, refcount**. Repeated maps increment refcount without a new attachment. On no context bank, attach failure, map failure or empty `sgl`, it returns error, unmaps the successful attachment if necessary, and detaches. [`msm_vidc_memory_unmap` lines 282–315](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_memory.c#L282-L315) unmaps and detaches on *last* mapping ref, resets the device address, and does not drop the exporter reference itself.

`msm_vidc_memory_unmap_completely` and `msm_vidc_unmap_buffers` ([driver lines 2382–2407 and 2767–2789](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vidc_driver.c#L2767-L2789)) drain mappings on teardown, and `msm_vidc_put_delayed_unmap` releases the extra ref when the special lifetime ends. **This is the lifetime that a new Iris two-device design must preserve**, not a license to copy the vendor's exact error-path implementation, which has some early-return allocations needing independent review.

A bypass/identity mapping is **not** a substitute for IOVA constraints.

## Alternatives evaluated

1. **Single shared translation domain on Iris parent:** *not accepted*. It is mechanically implementable with existing Iris code and might even be sufficient if the firmware/hardware tolerates both SID groups in one page-table context and a common collision-free address allocator. However reference compiled DT names two region devices and different lower pool addresses, and the downstream maps to two **distinct cb->dev** objects. Their ranges heavily overlap; that **does not** imply either equivalence or unavoidable conflict, because independent page tables can reuse numeric IOVAs. To approve a shared model requires a source- or hardware-backed proof of identical translations/access requirements for both classes, plus a validated allocator preserving constraints, including same DMA-buf mapped by both classes.
2. **Two parent `iommus` entries and no driver changes:** *rejected*. Pinned ARM SMMU attaches all stream matches of a single Linux device to its single context bank; both vb2 queues/internal buffers remain parent-owned.
3. **Two separately registered child DMA devices, one SID/mask each:** **recommended architecture**, conditionally. It reproduces the downstream device selection and can use existing DMA API per child; still needs an approved upstream child binding, class routing, domain/IOVA constraints and strict lifecycle/error unwinding before even a disabled prototype can be considered meaningful.
4. **Manually `iommu_map`/raw IOVA allocation, undocumented aux-domains, or identity/bypass:** *rejected for now*. This circumvents DMA-BUF/VB2 attachment ownership, DMA API cache coherency, automatic DMA cookie accounting and cleanup; no source evidence establishes required or safe semantics.

## Testable acceptance conditions (not results)

1. **Source/ABI:** reviewed child-node binding + Boot-owned *disabled* DT compiles/schema-checks; only one correct SID/mask per DMA child; no accidental parent-dual-IOMMU domain claim, no secure-session support implied. Exact known intended child `struct device *` and class->device mapping in code.
2. **Driver lifecycle / fault injection:** controlled -EPROBE_DEFER and second-child probe failure leave **zero** surviving registration, device links, DMA maps and references; repeated probe works. On imported DMA-bufs, test attach fail, map fail, empty SGL/multi-SG, success, duplicate fd/ref reuse, two-class import of same DMA-buf, unmap and detach once per mapping, streamoff/error/reset/close cleanup, delayed DPB/RBR release; map address invalidated after last unmap. Ensure secure-buffer import fails for nonsecure session.
3. **Allocator check:** observe distinct `iommu_get_dma_domain` for two child devices (and appropriate groups), both addresses within their source-backed min/max pools, no stale DMA mappings after teardown, and separate mappings/refcounts for a DMA-buf simultaneously present in both classes. Verify coherent/cache sync and direction correctness.
4. **Native hardware-only gate:** with real composed handset DT and correct firmware, log actual selected SIDs/domain IDs, programmed IOVA ranges, HFI firmware ACK, decode input/output/DPB and same-buffer dual-mapping stress. Verify no SMMU faults/aliasing on repeated allocation/streamoff/error. Never infer native success from QEMU or a source-schema pass.

**Concrete missing evidence before implementation approval:** a mainline-representable child device-tree and IOMMU group/domain topology preserving the two actual Motorola bank properties, a source-supported mechanism for enforcing both lower IOVA bounds, and confirmation that firmware/HFI accepts per-class IOVAs via these domains. RPMh/OPP and three-path ICC remain independently queued and **outside this assignment**. No changes to accepted `razr/integration`, Boot images, VPU kernel or physical device.
