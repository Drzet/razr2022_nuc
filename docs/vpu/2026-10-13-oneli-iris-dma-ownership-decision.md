# Oneli Iris nonsecure bitstream/pixel DMA ownership: eighth-round decision

**Date:** 2026-10-13. **Task:** eighth coordinator review, `docs/NEXT_TASKS.md` main blob `03f1e2c0e72f76fb7fb62d1a18e6ab7f63705339`, `docs/EIGHTH_REVIEW.md` blob `900d9be2788fb402a1564a03dd5fd31a36917bf3`. This is **one bounded source design decision**, not a device patch or a proposed enablement.

**Recommendation: KEEP TWO INDEPENDENT NONSECURE DMA-API DEVICES/DOMAINS** for oneli Iris, specifically a bitstream/nonpixel device and a pixel/DPB device. Use pinned, already-supported OF platform-child and DMA/VB2 interfaces. Do **not** create a parent `iommus` property with two SIDs and mistake that for two domains; do not add an unverified IOMMU auxiliary-domain implementation. Current driver architecture cannot implement this by device tree alone. **No kernel patch is authorized by the present evidence**, so Iris remains disabled in the accepted `razr/integration` commit `2b5acf108ae37040ac1e652e029bb37f5609e886`.

**Security versus allocator convenience:** `MSM_VIDC_NON_SECURE` and `MSM_VIDC_NON_SECURE_PIXEL` both use the nonsecure DMABUF-owner predicate and nonsecure heaps. Their separate domains do **not by themselves demonstrate an independent security policy or different VMID protection**; extra separation can reflect hardware stream routing, address-allocator bounds or buffer taxonomy. Conversely, sharing a nonsecure predicate does **not prove** SMMU domains are interchangeable. Secure video uses distinct heaps/VMIDs and remains explicitly **out of scope**; do not pass secure buffers through either proposed nonsecure device.

An address assertion after an invalid map is **fail closed and unwind**, not allocator correctness.

## Alternatives considered

| Alternative | Source verdict | Reason |
| --- | --- | --- |
| **A. Single Linux DMA domain, parent with both SIDs** | **Reject as oneli-equivalent now**; potentially testable as an explicitly reduced experimental fallback if independently authorized later | Both streams would be mapped by `arm_smmu_attach_dev` to one CB. To satisfy both stock address pools with a shared IOVA, allocations would have to remain in the *intersection* `[0x25800000,0xe0000000)`; stock has pixel-only lower addresses, and overlapping maxima do not prove firmware/hardware accept a combined map. Parent Iris's current DMA paths do not enforce this floor; `dma_mask` is insufficient. No pinned phone firmware/hardware evidence proves unifying two domains safe, or that video engines access identical IOVA mappings in both streams. |
| **B. Dedicated bitstream/nonpixel and pixel `struct device` children, each one SID** | **Recommended for a *future disabled implementation***, not ready for enabled board node | Matches the source's region-selected `cb->dev`, uses standard OF child devices with **separate IOMMU default DMA domains** and existing VB2 DMA-contig device selection. Requires a real binding, probe order/group validation, buffer owner wiring and rollback; upstream Iris currently has none of these. |
| C. Manual `iommu_attach_device` swaps, one device with two dynamically attached domains, guessed aux-domain/PASID | **Reject** | Same Linux device cannot safely switch a DMA-API attachment per buffer while concurrent HFI bitstream/pixel queues exist; pinned ARM SMMU driver attaches all fwspec IDs to one CB. No source-backed auxiliary-domain scheme for this hardware. |
| D. ## Exact proposed driver / binding seams (DESIGN ONLY, NO IMPLEMENTATION)

- **`Documentation/devicetree/bindings/media/qcom,sm8550-iris.yaml`**: add reviewable *two named nonsecure DMA consumer child devices* for SM8475, one `iommus = <&apps_smmu 0x2180 0x400>` and one `<&apps_smmu 0x2187 0x400>`, with a non-ambiguous role, provider cell descriptions and explicit allowed DMA ranges. Any proposed child `compatible`/binding schema must be independently reviewed by Boot/IOMMU maintainers; **no made-up compatible is asserted** here. Secure contexts remain absent/disabled. Parent video's two existing `iommus` entries must not be used as a pretend multi-domain attachment.
- **`drivers/media/platform/qcom/iris/iris_probe.c` / `iris_core.h`**: create/lookup actual child platform DMA devices by role, require **two distinct** resolved IOMMU groups/default DMA domains, hold device references, set/check per-device DMA limits, enforce missing/duplicate/misprobed sibling as `-EPROBE_DEFER` or hard failure as appropriate. Do **not** start media registration/streaming before both exist; never free devices while any DMA mapping, HFI queue or session is live.
- **`iris_vidc.c::iris_m2m_queue_init` / `iris_vb2.c`**: decoder compressed V4L2 OUTPUT queue -> nonpixel device; decoded V4L2 CAPTURE -> pixel device. Encoder mapping reverse. `vb2_dma_contig_memops` already imports an external DMABUF with *its selected device*; **do not implement a separate unreviewed importer**. Treat each queue (and each attachment) as owned by its DMA device, validate whole mapped span and preserve normal VB2 unmap/streamoff lifecycle.
- **`iris_buffer.c` / `iris_buffer.h`**: internal DPB pixel; codec scratch COMV/LINE/PERSIST/BIN nonpixel, only where pinned VPU buffer ABI maps them that way; retain allocation/mapping owner on each object and free against the same device. Reject secure-required types instead of silently routing them to a nonsecure mapping.
- **`iris_hfi_queue.c`**: interface queue table and SFR are **nonpixel** in the downstream source and need nonpixel DMA ownership for alloc/free. These are controller-core allocations outside ordinary per-session VB2.
- **`iris_firmware.c`**: PAS9 image loads into reserved **physical** carveout. Keep this separate from IOMMU-mapped video buffer IOVAs. Do not fold `0x9fd00000/0x700000` reserved-memory physical address into either DMA region.

## Lifecycle / negative tests required before authorizing even a disabled prototype

1. **Probe/schema gate:** schema and `dtbs_check` with exactly one child per *nonsecure* role, source-backed SID/mask, no active stock node. Probe must confirm two distinct IOMMU domains/groups or hard-fail; test missing, duplicate, mismatched/disabled child and supplier deferral. On failure, no video registrations, allocated HFI queues, DMA buffers, or orphan child devices.
2. **Allocation/address gate:** instrument DMA/sg paths and inject allocator failures, `dma_buf_attach` fail, `map_attachment` fail, non-contiguous/undersized SG, unsupported IOVA floor, and upper-bound/size overflow. Each error unwinds exactly one matching unmap/detach/put/free with **same device**; no stale DMA address. Reject wrong-region or secure DMABUF. Test the *complete* range, not only first SG address.
3. **Shared-buffer gate:** same DMABUF through two classes must create two independent region+device mappings/refcounts; never reuse one address from the other's domain. Include imported VB2 user buffers, kernel MMAP buffers, encoder/decode type inversion, internal DPB and nonpixel scratch. Explicit read-only/delayed DPB releases and failure after first mapping must leave no leaked attachment or pinned ref. Current downstream source's delayed-unmap/vendor attrs should **not** be assumed available upstream.
4. **Core/lifetime gate:** HFI command/message/debug queue and SFR live in nonpixel DMA context; session stop, streamoff, interrupted session, firmware fault, system suspend/remove and repeated probe/unbind must free all queues and buffers **before** deregistering child DMA devices. The parent IOMMU attachment is not used as a fallback. No need to implement secure video in this prototype.
5. **Hardware acceptance later:** on unlocked oneli, verify real attached SID/context-bank/domain identity, selected firmware compatibility and IOVA pools, PAS9/HFI startup and actual decoded-frame DMA. A host build or QEMU **cannot** establish the physical SMMU/device behavior.

**Specific blockers to implementation:** (i) no reviewed mainline binding/provider topology for two video child DMA consumers on this oneli board, (ii) no verified translation of each DMA floor/aperture in the upstream IOVA allocator from stock `virtual-addr-pool`, (iii) no tested firmware behavior confirming domain separation and queue IOVA constraints, and (iv) full internal buffer role/lifecycle owner wiring absent in Iris. Those missing inputs justify **stopping before even an isolated patch**, rather than committing a speculative child compatible or a fake equivalent `iommus` property.

**Boundary:** the source design is credible but **not compiled/implemented/hardware-tested**. It does not alter Boot's native diagnostic profile, accepted `razr/integration`, GPU/Power/USB/DP queues, or separate MXC/MMCX and three-path ICC holds. Coordinator should review this single decision before authorizing implementation.
