## New prerequisite finding: SAME architecture already being upstreamed

**The previously missing current-community search decisively finds the closest existing implementation:** Vikash Garodia et al., **[PATCH v5 00/13] media: iris: Migrate iommus to iris sub nodes**, submitted **2026-09-26**, Message-ID `20260926-vpu_iommu_iova_handling-v5-0-0322ca5dc10c@oss.qualcomm.com`, upstream series base `f5f84daefcd92d7a630066635ecea1433ed5eac7`, [cover and entire patch inventory](https://lists.openwall.net/linux-kernel/2026/09/26/358). Earlier v1 2026-07-09, v2 2026-07-31, v3 2026-09-09, v4 2026-09-14 are superseded. No newer version was found in the scoped 2026-10-13 search; this is not proof none exists.

Key upstream series parts to **reuse/adapt rather than independently replicate**:

1. [v5 01/13 common DT binding](https://lists.openwall.net/linux-kernel/2026/09/26/359): Iris **controller-owned `non-pixel` and `pixel` OF subnodes**, `#address-cells = <1>`, `#size-cells = <1>`, `dma-ranges`, single IOMMU per context; common `qcom,venus-common.yaml` owns the topology. This is **not** the project's two independent peer `qcom,sm8475-iris-nonpixel`/pixel compatibles with parent `qcom,dma-consumers` phandles.
2. [v5 04/13 IOMMU ranges](https://lists.openwall.net/linux-kernel/2026/09/26/362): reviewed-in-progress `iommu-ranges` on the **DMA consumer node**, with range-complement reservation in `drivers/iommu/of_iommu.c`. **Crucial ABI change:** following explicit upstream review, pure IOVA-only `iommu-addresses` without a physical `reg` is no longer the accepted direction, despite being supported by the pinned kernel implementation. A device-specific `iommu-ranges` is proposed and requires the [dt-schema PR #207](https://github.com/devicetree-org/dt-schema/pull/207). This is a targeted externally authored IOMMU core patch, NOT permission to invent our own IOMMU ABI.
3. [v5 05/13 context-device creation](https://lists.openwall.net/linux-kernel/2026/09/26/350): ordinary `platform_device_register_full` on `non-pixel`/`pixel` child OF nodes, DMA configuration on their devices, per-role devices, cleanup before/after V4L2 setup and on failure. No independent placeholder driver/probe or peer-phandle graph is needed.
4. [v5 06/13 buffer routing](https://lists.openwall.net/linux-kernel/2026/09/26/) and 07/13 parent DMA-mask handling: upstream authors also implement queue and internal/HFI ownership and preserve parent-IOMMU legacy platform compatibility. **Do not backport full buffer routing yet**; tenth assignment explicitly stops after foundation and SM8475 remains gated.
5. [v5 DTS examples](https://lists.openwall.net/linux-kernel/2026/09/26/355) show accepted-direction subnodes on newer VPU3x/4x/5x SoCs, with an explicit note from the cover: **VPU2x not migrated yet; its Iris subnode support is expected when it moves away from Venus.** SM8475 is an inferred VPU2 4-pipe/Gen2 candidate, so port **only minimal VPU2/SM8475-specific deltas** and honor hardware evidence rather than copying a later SoC's SIDs.
6. Separate active upstream [2026-09-15 HFI Gen2 on VPU2 4-pipe](https://lists.openwall.net/linux-kernel/2026/09/15/2174), Xilin Wu v2, extends existing SM8250 platform descriptor rather than duplicating an entire VPU2 driver. Keep its authorship and applicability in view; it does not resolve stock PAS acceptance.

**Current mainline status checked 2026-10-13:** `torvalds/linux:master` files `drivers/media/platform/qcom/iris/iris_resources.c` blob `2c4d34c7bd77d1f78d3572f659da656eb3b12113` and `drivers/iommu/of_iommu.c` blob `a18bb60f6f3dfdba853b6e16dd2a8616f6a731c7` still lack these v5 APIs. Thus this is **an unmerged series, not part of our pinned/mainline kernel**, and it cannot be assumed available until a provenance-preserving backport or newer accepted kernel is chosen. The v5 cover documents that an earlier dynamic `iommu-map`/synthetic-device approach was NAKed and subnodes are the maintainer-preferred interface.

**Maintained out-of-tree/mobile scope:** bounded 2026-10-13 public search of postmarketOS wiki/pmaports, SM8475/oneli ports, and Qualcomm mobile-Linux Iris work did **not reveal another device-specific production implementation stronger than Qualcomm's v5 series**. This was a web/index search, **not** a complete enumeration of all git refs. Previous pinned Android downstream **Waipio comparator** `LowTension/android_kernel_xiaomi_sm8475@39382bf760ccf05a8fb4dddee7138ecac02d4a59` remains a non-mainline source for vendor `virtual-addr-pool` and region-based `dma_buf_attach`; it is not a competing native mainline implementation. Earlier driver-local low IOVA workaround referenced in the v5 cover is superseded as preferred upstream design.

### Exact RESUME difference and firmware evidence

In [P's command construction](https://github.com/yzddmr6/linux-sm8450-liuqin/blob/fe81794b5e1b8a3f11a165f3acbfdb8fa671dbb3/drivers/media/platform/qcom/iris/iris_hfi_gen2_command.c#L867), a common `iris_hfi_gen2_session_resume(inst, plane, reason)` reads platform `resume_without_payload`. DRC supplies `HFI_CMD_SETTINGS_CHANGE` (`0x0100000c`); drain supplies `HFI_CMD_DRAIN` (`0x01000007`). The outer command remains `HFI_CMD_RESUME` (`0x01000008`), with response-required and interrupt-required flags, the selected port/session, and normal header/packet IDs.

| Encoding | Payload type / pointer / length | Serialized size for one RESUME |
| --- | --- | --- |
| P SM8450, flag true | `HFI_PAYLOAD_NONE`, `NULL`, `0` for **both** reasons | 32-byte packet + 32-byte header = **64 bytes**; no reason word |
| P other zero-initialized profiles; A; K; U | `HFI_PAYLOAD_U32`, address of reason, `sizeof(u32)` | 36-byte packet + 32-byte header = **68 bytes**; settings-change or drain word follows packet |

The sizes follow the eight-u32 header, eight-u32 packet prefix and `sizeof(*pkt) + payload_size` builder. The quirk is not a zero-valued reason, a change to PAUSE/DRAIN itself, omission of completion requests, firmware restart or a VPU-generation switch. P sets the flag only in `sm8450_data`; A has neither that profile nor the flag. [K's two RESUME functions](https://github.com/Drzet/linux/blob/905d2403c451838a408f6bb44e80a7cf9aa6ed10/drivers/media/platform/qcom/iris/iris_hfi_gen2_command.c#L1183) and [U's corresponding functions](https://github.com/torvalds/linux/blob/70dd4ee72eb2d5793c62e71c14e3aba78e5a4e56/drivers/media/platform/qcom/iris/iris_hfi_gen2_command.c#L1178) still always send the U32 reason.

There is stronger source support than the donor comment alone: [V `msm_vdec_session_resume()`](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/msm_vdec.c#L1307) sends `HFI_CMD_RESUME`, `HFI_PAYLOAD_NONE`, `NULL`, `0`. Its callers include input settings-change processing and `V4L2_DEC_CMD_START` after drain/last; [V's generic command serializer](https://github.com/LowTension/android_kernel_xiaomi_sm8475/blob/39382bf760ccf05a8fb4dddee7138ecac02d4a59/techpack/video/driver/vidc/src/venus_hfi.c#L3315) retains the same response/interrupt flags. It does **not** prove the chronological claim that every Iris2 firmware predates reason payloads, or identify Motorola's installed implementation. The older Motorola techpack snapshot previously rejected in the HFI audit remains unsuitable evidence for this question.
