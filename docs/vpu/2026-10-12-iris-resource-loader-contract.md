## Loader contract from actual pinned Linux code

**Relevant kernel sources:** `drivers/media/platform/qcom/iris/iris_firmware.c`, `iris_platform_vpu2.c`, `drivers/soc/qcom/mdt_loader.c`, `include/linux/soc/qcom/mdt_loader.h`, all at kernel RFC executable behavior at `7f1d729b6f458f1e76efe2894eb3c544bc9db856` (later **comment-only** evidence update `869cf4a6ad21afcc2435c4e2d1d4fa9ab33fb4bf`, no code behavior changed).

1. `iris_detect_firmware` reads **upstream property `firmware-name`**, not vendor `vidc,firmware-name`. SM8475 descriptor currently has **no built-in `.fwname`**. Missing property returns **`-ENOENT`** deliberately; this is not a codec hardware failure.
2. With an explicit property, `request_firmware(dev, value)` searches the normal Linux firmware locations. Neither Android's filesystem path `NON-HLOS:/image/vpu20_4v.mbn` nor bare stock `vidc,firmware-name = "vpu20_4v"` automatically installs that image in Linux.
3. **One practical proposed Debian layout**, based on *verified actual file bytes and code, not device execution*: install the exact public reference `vpu20_4v.mbn` in `/lib/firmware/qcom/vpu/vpu20_4v.mbn`; future **Boot-owned** `firmware-name = "qcom/vpu/vpu20_4v.mbn"`. This is a user-space packaging proposal, NOT a flash recipe and NOT PAS acceptance. Exact file SHA256 **`9582ea4c5565408bd3e5ba6f8fffc7881f226cae001b6fcd7a0c868de9add9af`**, 2,024,040 bytes, version **`video-firmware.2.4-33580ad5a949b4d45b3b008988280e60573cd894`**.
4. `qcom_mdt_get_size` checks an **ELF32 MDT-style program-header image** and computes the aligned PT_LOAD span. `qcom_mdt_load` / `qcom_mdt_load_no_init` choose **in-file MBN** versus **split MDT/Bxx** based on the *actual nonzero* `p_offset+p_filesz` relative to firmware length. In our previous **metadata-only** stock audit, all recorded `vpu20_4v.mbn` nonzero-load segment offsets lie inside the 2,024,040-byte MBN, making the non-split path structurally plausible; embedded hash-segment/PAS validity still need an explicit loader-format check before treating it as compatible.
5. **Alternative split install:** `/lib/firmware/qcom/vpu/vpu20_4v.mdt` (5,404 bytes, SHA256 `a276e19d4ba6f4b4b42bec7ee4497e1002582a357454d56e5e050d5f969c64b6`) with the actual phdr-indexed `vpu20_4v.b00..b09`, `.b18`, `.b19` in the **same directory**, preserving byte-identical names. Set future `firmware-name = "qcom/vpu/vpu20_4v.mdt"`. `mdt_loader.c::mdt_load_split_segment` replaces the last 3 filename bytes with `b%02d` using the **program-header index**, not sequential name count. The HFI request does **not** concatenate Bxx files. Including only the MDT, renaming segments, or installing them elsewhere will fail.
6. This SM8475 candidate declares **only Gen2** in its `iris_firmware_desc`. The optional `iris_detect_gen2_from_fwdata` heuristic runs *only if both Gen1 and Gen2 descriptors exist*. Therefore the recovered `video-firmware.2.4` version marker **does not dynamically select or prove Gen2 compatibility** on this candidate; the Gen2 choice remains a source hypothesis.
7. The Iris sequence is `of_reserved_mem_region_to_resource` -> `request_firmware` -> `qcom_mdt_get_size` / region fit -> `qcom_mdt_load(... PAS9 ...)` -> `qcom_pas_auth_and_reset(9)` -> `qcom_scm_mem_protect_video_var(...)`. It is **not** equivalent to signing verification merely because a host parser accepts the ELF/MDT header. Actual SCM firmware signing keys/security version and HFI Gen2 handshake are UNKNOWN without phone.

**Security/content boundary:** No proprietary firmware was checked into GitHub, and the exported FDT JSON contains derived non-sensitive property data only. A public-reference blob installed on Debian must not be represented as byte-verified firmware currently installed on the physical handset.

## Boot-facing disabled-node disposition

No runnable SM8475 VPU DT may be populated from this audit by guessing the remaining data. **Supported skeleton fields** are MMIO 0x0aa00000/0xf0000, IRQ174, reserved-memory 0x9fd00000/0x700000, source-based rate list, VIDCC/GCC clock/reset roles, two GDSC providers, two named nonsecure SIDs and upper IOVA ceiling. The **missing required translations** are: accepted mainline parent DMA device attachment for one/two vendor context banks, four-domain RPMh required-OPP provider/corner levels and source-specific 3-path ICC integration/bandwidth policy. The signed Linux firmware packaging path is proposed but **not integrated**. Boot retains sole DTS ownership and must run schema/dtbs_check on its eventual **disabled** node.

Per-FDT numerical GPIO/supply/status facts for USB, Power and AUX consumers are separately published in [six-FDT shared manifest](2026-10-12-oneli-stock-fdt-properties.json). Effective base+overlay composition is the Boot agent's responsibility. CPU/QEMU tests cannot validate native SM8475 VPU. The pending coordinator combined kernel may contain UBWC only as a separate provisional SoC prerequisite, **not** these VPU ancestors.

**Next exact evidence:** (i) mainline SMMU and VPU two-context upstream mapping semantics for SID 0x2180/0x2187, (ii) VIDEOCC->RPMh required-opps provider/corner mapping and frequency table, (iii) three ICC provider route mapping and DDR versus LLCC vote requirements, (iv) real signed firmware load/PAS/HFI/V4L2 on unlocked hardware. Until each necessary translation has evidence, keep VPU disabled.
