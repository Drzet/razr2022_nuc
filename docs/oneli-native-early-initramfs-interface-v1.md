# Native early-initramfs payload and boot image interface v1

**Boot proposal to Userspace (2026-10-12).** Machine-readable contract: [`configs/oneli-native-early-initramfs-interface-v1.json`](../configs/oneli-native-early-initramfs-interface-v1.json). This contract is **proposed, not acknowledged**. It supersedes the native-readiness/unknown-header *fields* of [v2 reference packaging](../configs/oneli-boot-packaging-v2.json), but does not replace the earlier [combined QEMU/Debian schema-v3 contract](boot_userspace_combined_artifact_contract_v1.md). Do not change either accepted build or previously tested Debian QEMU harness. Userspace must acknowledge the exact v1 before native payload-dependent packaging.

- Generated `kernel.config`: `c86c04cc707889c66f8e4a485d1bff70819c1747150cb211836f07efb9fff90e`.
- **Mainline oneli** `sm8475-motorola-oneli.dtb`: `d3c9abcea9950200babbcf6c979073dc94c6af5cac68578540ad570db4a14a03`.

These are accepted **source/build/QEMU** artifacts, not an established phone-boot placement. Never replace the mainline DTB with a DT assembled from stock property projections. QEMU `virt` continues to receive **QEMU's DT** and its own `console=ttyAMA0` profile, never oneli's board DT, command line or boot image. The new test is `/init` from this diagnostic cpio under that exact kernel, *without Debian rootfs*; it is distinct from completed Debian/systemd/SSH testing.

## 2. Exact Userspace payload delivery (v1)

Userspace supplies a directory `native-diag-v1/` and immutable manifest `oneli-diag-payload-v1.json`, next to `oneli-diag-initramfs.cpio` and `oneli-diag-initramfs.cpio.gz`. All paths in the manifest are **relative to the declared payload directory**; no absolute paths, path traversal or symlink traversal outside it. Mandatory metadata keys, compression and payload identity are in the machine-readable contract. Both compressed and uncompressed cpio SHA256 must be recorded and verified; include `/init` SHA256, accepted Image/DTB SHA256 and the exact kernel release. Empty requirement sets require explanatory config/scope evidence.

Produce a deterministic `newc` archive: only regular files, directories and deliberate symlinks/device nodes, sorted by C-locale relative pathname, numeric owner **UID:GID 0:0**, fixed entry mtime **0**, reproducible modes, **4-byte per-entry newc alignment**, terminating `TRAILER!!!`. Pre-create `/dev`, `/proc`, `/sys`, `/run`, `/tmp`; mark `/init` executable, and provide ARM64 static BusyBox or equivalently pinned no-dynamic-loader runtime with `/bin/sh`. Compress with `gzip -n -9`, suppressing wrapper original-name and timestamps. Pin package/tool checksums or exact version, and record executed commands. Userspace owns build implementation and must independently list/extract both cpio and gzip to verify numeric ownership, modes, content and ordering. The accepted kernel configuration must independently confirm `CONFIG_BLK_DEV_INITRD` and `CONFIG_RD_GZIP` before this compressed format is approved.

The initramfs uses **generic boot-v4 ramdisk** placement, not stock Android's vendor ramdisk. A separate vendor_boot **platform fragment** is a Boot-owned, purpose-built native container if the final header workflow needs one; it must not be silently fabricated by Userspace or copied from stock. For structural-only experiments: type **1** (platform), name `native-diag`, 16 deliberate zero board-ID words, table-entry size **108**, compression recorded independently. The platform fragment's contents and compression are **not** thereby hardware approved.

### PID1 and diagnostic behavior

`/init` must run as PID1, mount `proc` at `/proc`, `sysfs` at `/sys`, `devtmpfs` at `/dev`, and `tmpfs` at `/run`; report and retain mount failures. Record the kernel identity (`uname -a`), `/proc/cmdline`, `/proc/device-tree/compatible` (if mounted/readable), kernel log/probe errors where available, and an explicit diagnostic-ready marker with a monotonic sequence under `/run/oneli-diag`. Route a best-effort copy to `/dev/console` and `/dev/kmsg` where available; **absence of a physical receiving endpoint is not success**. Remain resident for observation; offer a bounded, explicit QEMU-only exit/shutdown trigger so CI can prove an actual PID1 reached and exercised diagnostics. Do not hang a CI test indefinitely or reboot the phone unconditionally.

No persistent partition mounts or writes, UFS root assumptions, fuse reads requiring elevated proprietary tools, firmware/authentication experiments, interactive network services, USB gadget, charge/thermal controls or guessed module autoloads. Derive any required .ko/firmware list from **this** minimal accepted config and chosen init, not all 1,702 compiled modules. An empty set must explain builtin coverage (UART, devtmpfs, proc/sysfs, decompressor etc.) and features intentionally disabled. Publish input and output hashes, archive listing, configuration proof, exact shell/tool versions and clean QEMU PID1/negative-test evidence.

## 3. Android boot-v4 and vendor_boot-v4 structural roles

Newly published VPU evidence at project `dadd330c3f09f715372da94091f04166f9f0c141` ([focused stock properties](vpu/evidence/focused-stock-properties.json)) closes stale v2 unknowns:
- Public **reference** `boot.img` SHA256 `287b3b5e3c61dec6a40f2b9203942b57533df206b0ed2ef16ecdb6bbe01e305d`: v4 header 1,584 bytes, 4,096-byte pages, **packed OS version 402653593**, **empty cmdline**, four **zero** reserved words, and **4,096-byte boot signature section** SHA256 `030600e25f969311812014a82fcb3edf10871be255cb59b74452d1e8926cf869`.
- Public **reference** `vendor_boot.img` SHA256 `1c27e22565f6f50919812bfcb5254cea2f3b629d98f5c26a7b54f5ece452036e`: v4 header 2,128 bytes, page 4,096, stock load addresses kernel `0x8000`, ramdisk `0x1000000`, tags `0x100`, DTB `0x1f00000`; vendor ramdisk legacy-LZ4, stock bootconfig **85 bytes**, single fragment table entry **108 bytes**. Stock vendor DTB region contains **two unpadded base FDTs**, MSM530/540; PVT DTBO index 3 matching PVT board-id is only a **reference candidate**.

The **unsigned host-only candidate** deliberately chooses `os_version_raw=0` (no asserted Android OS release), `signature_size=0` (no boot signature), four zero reserved words, empty boot cmdline/vendor cmdline and **zero bootconfig bytes**. This is an explicit choice, **not** a claim that these fields satisfy the Motorola loader. For a structural comparison, the reference addresses above may be supplied to existing `scripts/oneli_boot_v4_layout.py prototype` via explicit `--header-inputs` with `purpose=structural-only` and `phone_boot_validated=false`. Never silently inherit them as an approved native placement. Android boot-v4 signature and **AVB** on vbmeta/boot/vendor_boot/dtbo partitions are distinct; copying the stock signature never authenticates modified sections and this project currently supplies **no** native signing/AVB scheme.

The AOSP-derived reference packer/unpacker is independently pinned to `ntherning/mkbootimg@7209a7164f1772db43f92928012c86a00f6202ff` and the existing altered-size v4 fixture is tested in [`tests/test_oneli_boot_aosp_independent.py`](../tests/test_oneli_boot_aosp_independent.py). Its source-checked invocation is `mkbootimg.py --header_version 4 --kernel Image --ramdisk oneli-diag-initramfs.cpio.gz --cmdline '' --output boot-candidate.UNSIGNED.img`; vendor structure uses `--vendor_boot`, `--dtb`, `--vendor_ramdisk_fragment`, `--ramdisk_type platform`, `--ramdisk_name native-diag`, `--vendor_bootconfig`, `--pagesize 4096` plus **five explicit selected header/address fields**, as exercised in that pinned test. It is **not** a native flash command. Only after Userspace ships the payload can Boot independently unpack the new images and compare section bounds/hash/placement. Treat absence of source `boot.img` and `vendor_boot.img` binaries as a blocker to the *older template-based prototype*, not a reason to repeat full ROM scans.

## 4. Console evidence and observation gate

The [accepted mainline board DTS](https://github.com/Drzet/linux/blob/2b5acf108ae37040ac1e652e029bb37f5609e886/arch/arm64/boot/dts/qcom/sm8475-motorola-oneli.dts) declares `serial0=&uart7`, `/chosen/stdout-path = "serial0:115200n8"`, enables QUP0 wrapper and UART7 at `serial@99c000`. Pinned [Qualcomm GENI serial driver](https://github.com/Drzet/linux/blob/2b5acf108ae37040ac1e652e029bb37f5609e886/drivers/tty/serial/qcom_geni_serial.c) names the console `ttyMSM` and declares its OF earlycon for `qcom,geni-debug-uart`; ARM64 defconfig includes `CONFIG_SERIAL_QCOM_GENI=y` and `CONFIG_SERIAL_QCOM_GENI_CONSOLE=y`. Final generated .config and actual `/chosen` supplied by the bootloader must still be checked. GCC's seven PHY clock inputs are *not* upstream of this UART path per [source analysis](GCC_PHY_CLOCK_RECLASSIFICATION.md).

**No actual UART connector or safe voltage/ground/pinout has been established.** DTS GPIO26/27 pinctrl identifies SoC signals, **not** a reachable handset test point. The first physical observation must establish a safe serial receiver/ground path and measurable TX activity during attempted native boot, or an independently established alternative console transport. `console=ttyMSM0,115200n8` is a **source-derived candidate**, not a committed bootloader cmdline. The command line and whether a bootloader appends/replaces it are unresolved; host candidate explicitly leaves both cmdlines empty. Likewise `CONFIG_PSTORE_RAM=m` does **not** provide a persistent log: there is no approved ramoops reserved-memory carveout, retention guarantee or independent post-reboot readout. Do **not** allocate an invented region. Initial diagnostics require an actual observable output path or future accepted retained-memory design, not USB/DP.

## 5. Acceptance gates and sequencing

**First:** Boot publishes this versioned interface and asks Userspace to acknowledge it unchanged or explicitly propose a revision. **Second:** Userspace delivers the hashed diagnostic cpio, compressed file, manifest, actual accepted-kernel no-disk QEMU run and negative tests. **Third:** Boot packages a *host-validation-only* Android-v4 structural candidate, independently unpacks/hashes/verifies headers, 4,096 alignment, fragment table and bootconfig, and reports an explicit machine-readable blocked result for any unselected required input. No user download request, generic ROM scan, fresh full kernel build or hardware test occurs here.

**Unresolved/phone-only:** real Motorola header/address/DT selection and bootloader modifications; reference two-base + index3 effective *binary* composition (not the mainline tree); DTB handoff; physical UART and log capture; bootloader acceptance and AVB disposition. Separate source-solvable work is actual bounded FDT overlay apply using original hashed member bytes where available, and validating final payload with pinned pack/unpack tools. No native image is approved for flashing, no UFS-rootfs or peripheral activation, and no assertion of phone execution.
