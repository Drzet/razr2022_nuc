## Stock FDT: what is actually in the published typed export

Both independent `vendor_boot` *base* FDTs contain the same published GPU and GMU structure: `/soc/qcom,kgsl-3d0@3d00000` is locally `status = "ok"`, `qcom,adreno-gpu-gen7-4-0`, `qcom,gpu-model = "Adreno730v3"`; thirteen children `qcom,gpu-pwrlevel@0..12`; `/soc/qcom,gmu@3d69000` compatible `qcom,gen7-gmu`; `/soc/qcom,kgsl-3d0@3d00000/zap-shader` references `memory-region = <555>`, symbolically matching `/reserved-memory/gpu_microcode_region@8b91a000` with `reg = <0 0x8b91a000 0 0x2000>` (8 KiB). GPU raw interconnect cells **`<75 21 72 512>`**, name `gpu_icc_path`; these describe a GPU→memory path but **not** encoded `SH0/MC0/ACV` vote payloads. GMU `iommus` raw cells **`<546 5 0x400>`**; `vdd-supply` phandle 556 and `vddcx-supply` 545 remain distinct raw upstream resource relationships.

**Important export limitation discovered by reading the actual 15.9 MB file, not only its summary:** its `nodes_with_requested_properties` selection retains only each pwrlevel child's **`reg`**, not `qcom,gpu-freq`, `qcom,level`, `qcom,cx-level`, `qcom,bus-freq/min/max` or `qcom,acd-level`. The GPU parent selection also omits `qcom,bus-table-ddr`, `qcom,chipid` and any `qcom,initial-pwrlevel` / UBWC numeric property. Neither base's selected record contains those values, although node presence is proven. Hence the binary-export itself does **not** independently confirm the Motorola *numeric* table. It is a **filtered-property publication**, not a lossless DTB reconstruction; do not present source-transcribed numeric values as read back from stock FDT. The source-owned pinned `cape-gpu.dtsi` supports the numbers below. A **bounded six-FDT property-filter extension** could confirm those exact numeric fields using the existing VPU member bytes, if Boot/VPU need source-vs-binary comparison; it must **not** trigger another 4.35-GB ROM scan. The two base FDT source candidates have the same 13 pwrlevel node topology, not proven to have identical omitted cell values.

## Source-backed CX and bandwidth numeric disposition

These are **Motorola `cape-gpu.dtsi` source values**, not present in the filtered stock binary export. Boot's prior disabled 13-level GPU OPP table reproduces the GPU `qcom,level` values and passed compiled-FDT check [38174125440](https://github.com/Drzet/razr2022_nuc/actions/runs/38174125440). Mainline baseline GMU CX vote table derives from **200 and 500 MHz GMU OPP levels 64/128**, not thirteen GPU-linked `qcom,cx-level` values. Missing source proof: whether stock GMU firmware independently supplies the required per-GPU CX rail minimum and exactly how its oneli HFI `cx_arc_votes` and `gx_arc_votes` are evaluated. This cannot be inferred from found 57,272-byte GMU file or nominal WHENCE version.

Motorola's DDR `qcom,bus-table-ddr` source is twelve entries with MHz-equivalent factors `0,200,451,547,681,768,1555,1708,2092,2736,3196,3350`; nominal bandwidth arithmetic is `MHZ_TO_KBPS(mhz,4) = (mhz * 1000000 * 4) / 1024`. **These are KGSL interconnect bandwidth source requests, not host HFI indices or proven encoded BCM votes.** Pinned [mainline `a730_build_bw_table`](https://github.com/Drzet/linux/blob/3baaec593ae7c701e95e0c3df2d56c33d3aed4f3/drivers/gpu/drm/msm/adreno/a6xx_hfi.c#L680-L742) generates twelve **hardcoded** HFI `SH0/MC0/ACV` entries; current `a6xx_gmu_set_freq()` retains `bw_index=0` unless A730 gets explicitly supported `.bcms` and associated bandwidth OPP requirements. Twelve-on-twelve cardinality is not an index-equivalence proof.

**Result: hold both CX floor and DDR index translation** pending exact firmware/command-DB semantics and a meaningful mainline-vendor mapping. Do not copy `qcom,bus-freq = <11>` into HFI index 11; do not raise GX `opp-level` to approximate CX; do not invent `opp-peak-kBps` for the fixed hardware HFI table. A narrowly justified future A730-specific BCM and OPP bandwidth policy should be reviewed separately, with source-equivalent `SH0/MC0/ACV` payloads and GPU `MASTER_GFX3D → SLAVE_EBI1` provider paths. Actual firmware authentication and voltage performance remain hardware-only.
